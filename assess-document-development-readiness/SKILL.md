# 文档与实现开发就绪度评估

## 目标

判断现有材料和实现证据能否支持用户当前要做的决策，并发现会造成返工、语义漂移、任务失败、错误结果、数据损坏、越权泄露、不可恢复或错误发布的问题。

评估结束时必须回答：

1. 当前材料能够支持哪一个决策，不能支持哪一个决策；
2. 目标范围实际达到什么能力成熟度，各维度是否存在短板；
3. 哪些问题构成阻断或高风险，依据和失败链路是什么；
4. 文档、实现和验收分别需要补什么；
5. 满足哪些可观察、可复验条件后才允许进入下一阶段。

## 工作边界

- 只使用用户指定项目内的文档、代码、运行环境、数据、测试和已确认结论。
- 不读取相邻项目推导当前项目；同名概念也不能视为共享依据。
- 用户已说明开发方收到的是最新文件时，不再把历史副本或重名文件列为失败原因。
- 发现多个候选基准且用户未指定时，列出冲突并请求确认，不自行拼接。
- 不把目标架构、设计稿、计划或界面存在描述成已经实现的能力。
- 不主动改文档、改代码、生成开发口令或继续下一轮任务；用户另有要求时再执行。
- 不输出预估时间、开发天数或周期，除非用户明确要求。
- 不机械加入多人协作、多租户、复杂权限等能力。先判断是否属于当前范围；不适用项标记为“不适用”并说明理由。
- 不把无法验证直接写成产品缺陷。将其标记为“未验证”；只有缺少证据本身违反当前门禁，或缺失合同导致实现含义无法确定时，才构成阻断。

## 选择评估目的与深度

开始前先锁定用户要做的决策。用户未指定时，根据现有材料选择能够支持的最窄模式，并说明选择理由。

| 模式 | 要回答的问题 | 最低检查范围 | 不得输出的结论 |
| --- | --- | --- | --- |
| A 开发前筛查 | 文档能否约束指定范围的开发 | 基线、产品结果、对象与状态、关键交互、执行边界、验收合同 | 实现已完成、任务已闭环、可生产发布 |
| B 纵向闭环或阶段验收 | 指定用户任务是否真实完成 | 文档、源码、运行行为、请求、持久化、异常路径、验收证据 | 未检查范围已完成、整个产品可发布 |
| C 定向根因审计 | 已知失败或落差由什么造成 | 从失败任务反向追踪到最早根因及受影响范围 | 未受调查范围安全或可用 |
| D 生产准备与发布审计 | 指定发布范围能否安全上线并持续运行 | 所有适用层、风险抽样、发布物、恢复与残余风险 | 超出审计边界的整体发布保证 |

控制评估成本：

- A 模式以合同存在性、一致性和可执行性为主，不要求不存在的运行证据；生产维度只有在会改变当前开发决策或已经出现独立安全、数据风险时才展开，其余标记为“未评估”。
- B 模式围绕指定纵向任务取证，不展开与阶段无关的生产能力。
- C 模式找到能解释失败的最早根因后，继续确认影响范围和独立高风险，不把全项目重审作为默认动作。
- D 模式执行完整审计；高风险结论不能因节省成本而降级取证。
- 上游基线已经阻断下游判断时，停止无效的深层证明，把下游标记为“未评估”；仍记录已经发现的独立安全或数据风险。

## 证据与判断规则

将内容分为三类：

- **事实**：可由当前文档、源码、运行结果、接口、数据或测试直接证明。
- **推断**：由已知结构推导出的高概率风险，写明推导链和待验证点。
- **建议**：针对已识别问题提出的处理方式，不写成现状。

给关键判断标记证据等级：

| 等级 | 证据含义 | 可支持的典型判断 |
| --- | --- | --- |
| E0 | 无证据、证据冲突或只有未确认口述 | 只能标记未知或待确认 |
| E1 | 权威文档、合同或已确认决策 | 可证明要求已定义，不能证明已实现 |
| E2 | 源码、配置、静态产物或测试设计 | 可证明存在实现路径，不能单独证明运行结果 |
| E3 | 在目标环境观察到真实请求、状态变化和持久化结果 | 可证明本次受测任务行为 |
| E4 | 可重复测试、发布记录、恢复演练或生产等价证据 | 可支持阶段验收或限定范围的发布门禁 |

证据强度使用以下结论：

- **充分**：关键判断达到当前模式要求的证据等级，风险抽样与审计范围匹配，且没有未解释的冲突。
- **受限**：部分关键证据缺失，但现有证据仍能支持一个更窄的结论；明确降低结论范围。
- **不足**：关键证据缺失或冲突，无法支持用户要做的决策。

每个 P0 和 P1 必须包含：

1. 证据、证据冲突或缺失的必要合同；
2. 会在哪条真实任务中触发；
3. 具体失败结果；
4. 最小修复要求；
5. 可执行的通过门禁。

缺少完整失败链路的通用担忧不得列为 P0。文档没有写某项内容时，先证明该内容对于当前决策和失败后果是必要的，再判断严重度。

## 评估流程

### 1. 锁定决策基线

记录：

- 项目、评估模式和明确排除范围；
- 当前要做的决策及其责任人；
- 权威文档及各自职责；
- 当前阶段和目标发布边界；
- 是否存在代码、可运行环境、真实或代表性数据、测试和发布证据；
- 用户定义的首个可用结果与关键失败后果；
- 已确认暂缓或不开发的能力。

文档职责至少区分产品功能、对象与规则、UI 与交互、阶段范围、技术合同和验收标准。文档冲突时指出具体字段、适用范围和影响，不用“文档不清晰”概括。

### 2. 建立能力剖面

分别判断以下维度，使用“已定义、已实现、已观察、可重复证明、不适用”标记状态，并附证据等级：

| 维度 | 判断内容 |
| --- | --- |
| 界面与交互 | 入口、反馈、状态变化、返回、撤销、取消和刷新恢复 |
| 领域与数据 | 核心对象、关系、状态、版本、所有权和持久化 |
| 执行与集成 | 前后端、服务、队列、文件、AI、外部系统和失败补偿 |
| 信任与安全 | 身份、权限、隔离、敏感数据、内容资格和审计 |
| 恢复与运营 | 重试、恢复、监控、部署、回滚、迁移和人工处置 |
| 验收与发布 | 需求追踪、可重复测试、批准内容和最终发布物的一致性 |

再给出便于沟通的总体成熟度：

| 等级 | 判定标准 |
| --- | --- |
| L0 布局 | 页面、入口、槽位或占位存在 |
| L1 交互 | 控件可操作，具有真实状态变化和基本恢复行为 |
| L2 闭环 | 接入真实数据、持久化、服务和上下游，能够完成指定用户任务 |
| L3 生产 | 所有适用生产维度达到发布门禁，能够安全运行、恢复和处置 |

总体等级不得掩盖维度短板。不得用某个维度的高等级补偿另一个关键维度的缺失，也不得用 L0 或 L1 证明 L2/L3。

只有实现状态已知时才分配 L0–L3。材料明确说明尚无实现时标记为“未实现”；实现证据不足时标记为“未验证”，不得创造“低于 L0”等额外等级。

### 3. 按风险选择任务

根据模式和风险选择任务，不机械限定为一条：

- A 模式选择一条主要价值任务，检查合同能否完整约束它。
- B 模式至少覆盖用户指定的主要任务；若适用，再覆盖最高影响的异常路径。
- C 模式从已知失败任务开始，补查与其共享根因或共享状态的任务。
- D 模式覆盖主要价值任务，并按适用性增加：最高权限任务、最具破坏性或不可逆的写操作、异步或长任务、AI 或外部集成任务、恢复或退出任务。

对选中任务检查：

- 首次进入和正常完成；
- 输入缺失、冲突和边界数据；
- 中途刷新、返回和页面关闭；
- 失败、超时、重复提交、取消和重试；
- 上游修改后的下游失效范围；
- 版本恢复是否污染当前内容；
- 批准内容、生成结果、导出物和发布物是否一致；
- 权限变化、并发操作或外部依赖变化是否会改变结果。

已有代码时交叉检查源码、运行行为、网络请求、持久化结果和测试。只读源码或只看截图不足以证明任务闭环。无法运行时说明限制，不补写运行结论。

### 4. 按层审计

各层使用单一划分维度。把同一根因归入最早产生问题的层，其他层只记录影响，避免重复。

#### 第 0 层：输入与范围合同

检查权威来源、确认状态、包含与排除范围、冲突裁决规则，以及需求到对象、页面、服务和测试的追踪关系。

典型阻断：项目材料污染；职责冲突；未决条件由开发方自行补全；范围冻结后仍无法确定实现含义。

#### 第 1 层：产品结果与完成合同

检查首个可用结果、完整用户任务、完成语义、阶段成熟度和用户结果与页面范围的关系。

典型阻断：只要求覆盖页面；“完整 UI”没有交互或数据等级；生成、保存、批准、导出和发布混为一谈。

#### 第 2 层：领域与状态合同

检查核心对象、稳定 ID、关系、所有权、状态转换、版本绑定、失效规则、删除归档、恢复保留、分支合并和历史复现。

典型阻断：接口存在但没有统一领域模型；正文与检查结果属于不同版本；批准后可静默修改；历史结果只能重新生成。

#### 第 3 层：交互合同

检查触发条件、权限、输入、状态变化、持久化位置、加载与异常状态、撤销取消、刷新恢复、区域联动，以及适用范围内的可访问性和终端兼容要求。

典型阻断：控件只改变视觉；固定显示成功；禁用占位与已实现能力无法区分；用户无法识别结果是否真实或过期。

#### 第 4 层：执行与集成合同

检查系统职责边界、API 输入输出与错误、权限、幂等性、长任务快照与归属、事务和补偿、材料解析、并发处理、性能容量、接口版本及数据迁移影响。

典型阻断：模拟数据被当成业务能力；旧任务覆盖新内容；部分成功留下矛盾状态；上传成功但内容未完整解析；真实规模下无法完成关键任务。

#### 第 5 层：AI 可靠性合同

仅在产品包含 AI 时检查硬规则、模型判断和人工决策边界；输入与证据快照；结构和语义校验；事实冲突与不确定性；提示词注入、敏感信息外发和留存；质量回归；暂停、降级与人工接管。

典型阻断：把事实有效性、权限或硬性规则交给提示词；合法 JSON 被直接视为正确结果；没有代表性任务集验证模型或提示词变化。

#### 第 6 层：信任、安全与合规合同

按范围检查身份与授权、隔离、数据分级与脱敏、日志与第三方发送、删除保留、素材和内容资格、审批审计，以及适用的隐私、行业或地区要求。

典型阻断：前端隐藏按钮代替后端授权；无权公开的内容进入发布；版本历史被当作审计日志；敏感数据越界发送或无法删除。

#### 第 7 层：发布、运营与恢复合同

检查部署与回滚、配置和迁移、卡死与重复任务查询、安全重试与取消、过期结果隔离、人工修复、备份恢复演练、业务健康监控、供应商变化、数据导出和项目退出。

典型阻断：用户只能看到“处理中”；无法定位失败步骤；有备份但无法完整恢复；发布失败后无法安全回滚；依赖变化后没有处置路径。

#### 第 8 层：验收与交接合同

检查验收能否证明用户结果、真实请求与持久化、失败和权限边界、AI 质量、目标规模、干净环境复验，以及证据与需求、执行结果和发布物的对应关系。

典型阻断：截图替代业务测试；只检查路由和页面可见；关闭关键质量规则后仍宣称通过；测试结果无法对应批准版本。

### 5. 评定严重度

按失败后果和当前决策分级：

- **P0 阻断**：会导致核心任务无法完成、错误结果被当成成功、数据损坏或丢失、越权泄露、不可恢复、错误发布，或当前材料无法确定目标范围的实现含义。
- **P1 高风险**：核心任务可能完成，但在常见异常、目标规模、依赖变化或维护中高度可能返工、失效或形成不可接受的残余风险。
- **P2 改进**：不影响当前决策和闭环，可后续改善体验、效率或可维护性。
- **未验证**：证据不足，当前不能确认通过或失败；说明补证方式和它限制了哪个结论。

不要按实现复杂度或文档篇幅决定优先级。严重度随评估范围和阶段变化；同一问题在原型阶段可能是 P2，在生产发布阶段可能是 P0。

### 6. 给出限定范围的结论

只能使用以下结论之一：

- **不具备开发条件**：指定范围的输入基线或核心语义仍无法确定。
- **可进入受限原型**：仅允许验证结构、交互或技术难点，不得宣称业务可用。
- **可进入指定纵向闭环开发**：关键合同足以支持指定真实任务，其他范围继续冻结。
- **可进入阶段性扩展**：指定纵向闭环已通过可重复验收，可以按已确认范围扩展。
- **可进入生产准备**：指定 L2 闭环成立，开始关闭权限、安全、性能、恢复、发布和运营门禁。
- **具备生产发布条件**：限定发布范围内的适用 P0 已关闭；关键任务具有 E4 证据；适用生产维度已通过；P1 已关闭或由有权责任人明确接受并设有缓解与监测；批准内容、发布物、回滚和恢复证据一致。

结论必须同时写明评估模式、适用范围、证据强度和未评估范围。不得从 A 模式直接推导实现或生产结论，也不得把抽样通过扩展为整个产品通过。

## 审计过程安全

- 只读取完成当前判断所需的最少数据和日志，优先使用测试环境、代表性数据或脱敏样本。
- 不在输出中复制密钥、令牌、完整个人信息、商业机密或不必要的原始日志；用字段名、摘要和受控证据位置代替。
- 不为取证执行会写入、删除、发布、付费、通知外部人员或改变生产状态的动作。确需执行时，先说明目标、影响和恢复方式并取得明确授权。
- 发现真实敏感数据暴露时，只报告必要范围、影响和修复门禁，不扩大访问或传播。

## 输出格式

默认先给决策摘要，把详细证据放在问题表中；只在用户要求或审计留档需要时输出完整逐项清单。

### 1. 结论

- 当前结论、评估模式和适用范围；
- 允许进入与禁止进入的范围；
- 总体成熟度及关键维度短板；
- 证据强度、未验证和未评估范围。

### 2. 主要风险

按依赖和后果列出最重要的 P0、P1。默认先展示最多五项；其余进入分层问题表。后项依赖前项时明确说明。

### 3. 分层问题

| 层级 | 严重度 | 问题 | 类型与证据等级 | 触发场景与后果 | 最小修复要求 | 通过门禁 |
| --- | --- | --- | --- | --- | --- | --- |

只列真实成立或有清晰推导链的问题。相同根因合并；在“类型与证据等级”中明确标记事实、推断或未验证，建议只写入“最小修复要求”。

### 4. 分责补充

区分：

- 文档必须补充的合同；
- 实现必须完成的能力；
- 验收必须提供的证据；
- 需要有权责任人接受的残余风险。

### 5. 下一阶段门禁

按依赖顺序给出可观察、可操作、可复验条件。禁止使用“基本完成”“大致可用”“后续优化”等模糊表述，不默认输出开发时长。

## 质量检查

提交前确认：

- 是否先锁定了评估目的、模式、决策范围和关键失败后果；
- 检查深度和任务抽样是否与当前风险匹配；
- 是否只使用当前项目材料，没有把历史副本问题误判为开发失败原因；
- 是否同时给出分维能力状态和总体 L0/L1/L2/L3；
- 是否区分事实、推断、建议、未验证和未评估；
- 关键结论是否达到当前模式要求的证据等级；
- 每个 P0/P1 是否有触发场景、具体后果、最小修复和门禁；
- 是否把缺少文档内容直接当作缺陷，而没有证明其必要性；
- 是否合并重复根因并排除无关通用能力；
- 是否把目标态、计划、源码存在或单次演示写成已验收事实；
- 生产结论是否处理了 P1 残余风险、目标规模、回滚、恢复和发布物一致性；
- 取证和输出是否遵守最小访问、脱敏和非破坏性要求；
- 是否擅自改文档、改代码、扩展下一轮任务或输出未经请求的工期。

任一项不满足时，先修正评估再输出。
