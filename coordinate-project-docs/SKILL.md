# 项目推进与文档维护

以本阶段能够有效推进并检查成果为目标。先判断工作需要，再选择文档；优先更新已有文件，按缺口新增。让首次接手的人能找到有效依据、实际状态、重要未知和可执行的下一步。

## 1. 确定本次范围并读取现状

1. 依据用户点名的项目确定根目录或资料集合。隔离不同项目的要求、角色、状态和证据；不要因为文件相邻就混用。
2. 读取适用的项目规则和入口；用文件清单与定向搜索寻找有效需求、方案、参考、任务、决策和验收材料。先盘点，再读取与本次阶段相关的内容，避免全库灌入上下文。
3. 有成果时检查对应源码、稿件、素材、测试或运行记录。把历史报告作为线索；缺少访问条件时标明未核实，不把历史状态写成新验收结果。
4. 提取已确认目标与范围、重要约束、有效选择、已有成果、未确认问题，以及用户本次授权的工作。按确认状态、适用范围和明确替代关系识别有效依据；不按修改时间机械排序。
5. 仅对会改变目标、主要方案或推进条件且无法从资料解决的缺口提问。继续完成不依赖答案的整理；其他未知明确记录，不编造结论。

需要只读建议时只提出安排；用户要求建立、整理或同步时，在已有授权范围内完成必要文档修订，不逐文件重复请示。遵守用户已有的停点和范围；文档工作不自动授权代码开发、生图、发布、生产恢复、删除文件或写长期用户记忆。

## 2. 判断阶段与当前推进条件

按当前要处理的成果或模块判断阶段，允许一个项目同时存在探索、执行和验收中的不同模块。区分：

- 初始想法：明确目标、使用情境、关键未知和需要验证的假设。
- 方向探索：比较候选、参考与实验，形成足以作出选择的证据。
- 实施准备：明确本轮范围、可检查结果、必要方案与依赖，形成执行任务。
- 执行中：核对成果、更新任务与证据，处理已发现的差距和重要变化。
- 验收或阶段收束：依据有效标准核对结果，登记缺陷、剩余项和接续条件。

区分建立顺序、开工读取顺序和变更同步顺序。先有足以指导本轮工作的目标、要求与检查标准，再确定相应方案和任务；规则、入口、进度和决策按需要同步建立。不要要求整个项目一次性冻结，也不要提前填造后续架构、素材方案或验收结论。

按阶段和项目类型选择内容时，读取 [阶段与项目类型](references/stages-and-profiles.md)。

## 3. 指定信息的维护位置与对应关系

建立一份简短映射，优先采用项目现有文件名和组织方式：

| 信息职责 | 需要回答的问题 |
|---|---|
| 目标与需求 | 做什么、为谁、范围和预期结果是什么？ |
| 验收标准 | 什么观察或检查能判断本轮结果满足要求？ |
| 实施或制作方案 | 如何满足要求，依赖、取舍和关键未知是什么？ |
| 执行任务与进度 | 做哪些工作，先后条件、实际状态和下一步是什么？ |
| 决策 | 确认了什么、依据和理由、影响及替代关系是什么？ |
| 证据与验收结果 | 实际检查了什么，结果和未核实范围是什么？ |
| 项目入口 | 当前有效资料、成果、状态和接续位置在哪里？ |
| Agent 规则 | AI 如何读取、执行、检查和维护这些记录？ |

一份文件可以承担多个职责；同一种信息只指定一个当前主要维护位置，其他文件放链接或必要短摘要。沿用现有规格、状态表和控制台，不强制补齐 spec.md、plan.md、tasks.md 或 handoff.md。小任务可使用一份工作记录，无需完整目录。

维持以下对应关系：已确认目标与选择 → 当前要求和验收标准 → 相应方案 → 执行任务 → 成果位置 → 检查证据和结果。本轮已确认且准备执行的关键要求应有对应任务和检查方式；后续范围与未定要求保留待决身份。关键任务不得脱离目标。可使用已有编号或直接链接到具体条目，不强制新增复杂编号系统。

把项目入口用于导航，把 AGENTS.md 用于稳定执行规则；不把它们当作产品行为的替代规格。需求规定预期，源码或成果反映实际；两者不一致时登记差距。不要因现有实现较简单而降低已确认的目标。

## 4. 选择最少必要改动并执行

1. 依据缺口列出沿用、更新和新增的文档及其作用。只新增会改变行动、判断或接续条件的内容，不建立空壳文件。
2. 修改共享文件前核对最新内容或版本；发现并行更新时保留并合并有效内容，不能以旧副本覆盖。无法确定的冲突明确记录，并继续不依赖冲突的工作。在授权范围内就地整合有效内容，修正过期的现役表述；保留有用的历史和证据，并明确其历史身份。不要未经授权删除或移动原始资料。
3. 沿用现有格式，补足用途、范围、依据、状态和必要更新条件。区分已确认、提案、假设、待验证和历史内容。
4. 让任务具备来源、前置条件、可观察的完成条件和下一步；必要时先安排小范围验证，再展开制作。
5. 为长期协作且需要稳定规则的项目建立或更新项目级 AGENTS.md。仅放读取顺序、关键边界、已核实的执行与检查方式、记录维护触发条件；当前进度、详细需求及本轮临时授权和停点放在相应工作记录中，通过链接引用，不固化为长期禁令。无法核实的命令不要编造。
6. 按环境规定保存并核对可访问性。使用真实路径或可用链接，避免承诺不同工具或新对话会自动读取文件。没有可写目标时交付可用草稿，标明保存与文件依赖检查尚未完成。

创建或修改具体文档前，读取 [文档合同与同步规则](references/artifact-contracts.md)，只应用本轮相关合同。

## 5. 按事件维护，保持当前依据一致

- 用户确认重要变化：记录决策及替代关系，同步当前要求，再检查受影响的方案、任务、验收与入口。判断已有证据是否仍适用；受影响且未重新检查的项标为待验证，保留旧结果的版本和历史身份。用户当前明确的新要求应落实到有效规格，不再为同一决定重复请求批准。
- 新增方案或发现：标明提案或假设；根据影响安排验证或待决项，不写成已接受的选择。
- 执行或检查有新结果：更新进度和证据，分别记录实现、验证和交付状态。相关实现改变时检查旧证据的适用性，只重验受影响且必要的范围。缺少证据时保留未核实状态。
- 验收出现差距：形成补救任务；必要时提出目标或方案调整，获得相应确认后再同步要求。
- 阶段结束或中断：保存实际断点、成果入口、未完成项和继续条件。只有实际需要交出或接手时才组织交接材料，不每轮生成交接包。

将本项目需要的这些触发条件写入可访问的执行规则。维护发生在代理开展工作时，不承诺对话外后台监控。

## 6. 检查并交付可执行结果

检查有效要求、参考、任务、状态与验收是否冲突或缺漏；检查链接、版本和替代关系是否明确；确认没有把文档齐全、代码存在或历史测试通过写成当前整体验收完成。

只运行与本轮改动相称的检查：文档整理核对内容和链接；需要确认运行事实且处于授权范围时运行相关验证。无法检查的事项保留开放状态，不为文档工作附带开展整项目整改。

先说明当前推进条件和本次结果，再简要交付：

1. 当前处理的阶段或模块，以及仍影响推进的未知。
2. 沿用、更新或新增的文件及可访问入口。
3. 已确认选择、执行依据与真实状态；注明哪些仅引用旧记录。
4. 本次检查和仍未验证的事项。
5. 下一项具体工作、开始条件与完成证据；用户已授权执行时按范围继续，未授权的生产操作等单独保留。

需要专门方法时，可调用已可用的需求规划、就绪评估、知识整理或交接 Skill；遵守其适用范围和本次授权，不要求安装固定工具组合。本 Skill 的判断与文档工作可独立完成。
