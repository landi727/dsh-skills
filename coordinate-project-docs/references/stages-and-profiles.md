# 阶段与项目类型

按本轮成果选择足够支撑推进的内容。表中是职责，不是必须新增的文件清单。

| 阶段 | 需要的最少信息 | 推进条件 |
|---|---|---|
| 初始想法 | 目标、使用情境、范围线索、关键问题或假设 | 能明确下一项探索或验证要解决什么 |
| 探索方向 | 候选、有效参考、比较维度、试验结果、待选问题 | 本轮选择有依据；仍未确定的部分可继续探索 |
| 实施准备 | 本轮要求与验收标准、必要方案、依赖、任务 | 关键歧义不妨碍本轮执行；关键风险有验证安排 |
| 执行中 | 有效要求、任务与状态、成果位置、发现与证据 | 下一任务前置条件具备；变化已同步 |
| 验收或收束 | 检查结果、缺陷与剩余项、交付入口、继续条件 | 状态可核实，未完成项可继续执行 |

对已有项目从实际断点进入；先核查原有资料的职责覆盖和现役性，不重做启动全套。

## 按项目类型选择方案与证据

| 类型 | 要求与方案重点 | 可用证据 |
|---|---|---|
| 软件开发 | 用户流程、状态与异常、数据保存和恢复、接口、运行和发布边界 | 直接检查源码、针对性测试、运行观察、实际导出或恢复结果 |
| 视觉制作或交互网站 | 有效参考和版本、角色与构图约束、素材与分层、静态效果和动态行为 | 同区域对照图、有效素材、实际操作录屏、不同必要视口观察 |
| 研究 | 研究问题、范围、依据要求、分析方法、待证假设 | 原始资料与来源、可复查的分析过程、结论与证据对应 |
| 写作或内容 | 读者、目的、事实与结构、语气和交付约束 | 对应原始材料、事实核对、结构与编辑检查、实际稿件和排版 |

混合项目按成果使用多个类型；不要给纯视觉或写作任务硬造数据库、API 或部署方案。

## 常见分支

- 目标模糊：先组织问题与验证任务。保留未知，不写成冻结规格。
- 方向尚未确定：为探索定义可比较的结果；遵守用户关于生图或制作的停点。
- 要求已确认但方案未知：先补本轮关键方案和验证，随后拆执行任务。
- 有代码或素材但缺验收：核对实际状态并建立检查任务；分别记录实现和验证。
- 当前要求与实现冲突：保留要求并记录差距；发现不可行时提出选择，不擅自降级。
- 旧控制台混有失效规则：把有效入口说清，给历史段落标注身份；保留追溯依据。
- 只有一个小成果：在已有工作记录中合并目标、动作和验收即可。

## 对已有专门流程的使用

已有 Spec Kit 结构时保留其需求、方案、任务和编号体系。只做只读就绪评估时使用相应评估流程；文档与成果收束使用知识整理方法；明确换对话或接手时使用项目交接方法。不要把本 Skill 的使用当成对所有后续阶段的授权，也不要复制这些 Skill 的完整流程作为项目事实。
