# 标杆驱动初版设计

把概念需求转化为能够判断方向的初版设计。按“问题识别 → 市场验证 → 方案取舍 → 架构推导”完成内部工作，并根据任务尺度决定输出范围。

## 工作边界

- 保留用户已经确定的目标、约束和选择，不擅自扩大任务。
- 将旧方案视为背景材料，重新判断其合理性，不默认沿用原有结构。
- 交付停在初版架构。页面级交互、视觉设计、技术方案和开发排期只有在用户另行要求时才继续。
- 控制首轮信息量，同时提供足够的解释，使用户能够理解问题、市场解法、当前取舍和架构来源。

## 先判断任务尺度

每次执行先根据用户当前请求选择模式。不得因为对话正在讨论某个产品，自动把局部问题扩展成完整产品设计。

### 完整设计模式

用户要求完整初版设计、整体架构重构或系统级方案，并希望通过市场研究确认问题与方向时使用。执行全部流程，并使用五部分完整输出结构。

### 聚焦模式

用户明确点名本 Skill，但当前只询问单一功能、局部机制、具体取舍或已有方案中的一个问题时使用。只执行与当前问题直接有关的步骤：

- 确定当前要作出的具体判断及相关约束。
- 只在市场现状会影响判断或用户明确要求时，研究对应案例与机制。
- 将结论转化为局部能力、运行规则或对现有架构的影响。
- 回答到当前决策能够成立为止，不重新生成三个最重要问题、最难问题和完整初版架构。

概念解释、简单判断、状态澄清和后续局部追问不需要本 Skill 的专门流程。即使本 Skill 已进入当前对话，也要按当前问题控制范围。

## 1. 明确输入

从用户材料中提取：

- 目标用户与使用场景。
- 核心任务与预期结果。
- 项目所处阶段。
- 平台、资源、时间、技术和组织约束。
- 已确定的要求、可重新讨论的设想、尚未验证的假设。
- 已有资产、旧方案及迁移成本。

只追问会改变问题定义、案例选择、方案方向或模块架构的缺失信息。其余信息采用暂定假设；只在假设会影响结论时向用户说明。

## 2. 形成问题假设并允许研究修正

研究前先识别候选问题，研究后依据证据重新排序。不得先决定答案，再寻找支持材料。

### 最重要的三个问题

“最重要”表示问题直接决定产品价值及核心任务能否有效完成。沿用户任务全过程、业务对象状态变化和环节交接寻找障碍，并判断：

- 解决后能否明显提高产品价值。
- 出现频率或影响范围是否足够高。
- 未解决会造成什么结果。
- 是否影响多个后续环节。

最终保留三个互相区分、共同覆盖核心价值的问题。合并同义问题，删除仅影响局部表现的问题。

### 最难解决的问题

“最难”表示问题直接影响方案能否成立，并包含真实冲突、取舍或不确定性。检查：

- 多个目标是否彼此牵制。
- 一个选择是否会牺牲另一部分体验。
- 是否跨越多个任务、业务对象或模块。
- 技术、资源、平台或用户习惯是否形成明显限制。
- 市场是否缺少稳定、统一的成熟解法。

按实际情况保留难点，不为数量完整而补足。重要问题与难点指向同一对象时，仍分别解释“为什么值得解决”和“为什么难以解决”，避免复述同一段内容。

## 3. 围绕问题研究当前标杆

每次执行都查看当前资料，不依赖模型记忆给出市场排名。

先建立一个可扩充的共享候选案例池，再将案例映射到各个问题；已有证据可以复用，证据缺口进行定向补查。候选范围包括：

- 直接同类产品。
- 相邻领域的成熟产品。
- 对某一具体机制处理突出的产品。

同一产品可以对应多个问题。每个问题选出本轮研究范围内机制最成熟、证据最充分的三个案例；证据不足三例时，说明研究边界并保留已验证案例，不凑排名。

按以下依据进行问题内排序：

- 与当前问题的匹配程度。
- 实际流程和状态处理的完整程度。
- 对相关冲突与限制的处理程度。
- 可核验材料的充分程度。

分别控制三类结论的强度：

- **机制完整**：由官方文档、帮助中心、实际产品流程或演示证明产品采用了什么做法。
- **适配当前需求**：基于当前项目目标与约束作出分析判断。
- **效果得到验证**：需要用户数据、实验结果、可靠研究或可信第三方材料支持。

缺少效果证据时，只评价机制成熟度、流程完整度和当前需求适配度。宣传资料只能证明产品怎样描述自身能力。

内部为每个有效案例保留一条简短证据链：

> 问题 → 产品方法 → 证据来源 → 适用条件 → 代价与限制 → 对本项目的启示

明确区分：

- **可核验事实**：产品确实采用的做法。
- **分析判断**：做法可能有效的原因及适用场景。
- **项目假设**：迁移到当前项目后仍需验证的结果。

“本轮未找到相关证据”只表示当前研究边界，不推导为市场上不存在相关方案。

## 4. 提取机制并完成方案取舍

提取案例解决问题的机制，不照搬界面形式、模块名称或导航结构。重点判断机制如何分配职责、安排决策顺序、减少重复操作、管理状态或处理目标冲突。

综合设计前检查多个机制能否共存，并回答：

- 采用哪些机制，各自解决哪个问题。
- 哪些地方需要结合当前需求调整，依据是什么。
- 组合后，用户能否连续完成核心任务。
- 是否产生职责重叠、重复操作、数据归属冲突或新的认知负担。
- 初版能够承担哪些实现与迁移成本。
- 哪些内容延后，延后会产生什么影响。

只比较会改变方向的方案分歧。避免把多款成熟产品的功能直接拼接；每个设计选择都要对应已识别的问题、当前约束和可追溯证据。最后给出明确推荐及主要取舍。

### 将结论转化为设计承接项

在划分模块前，将每项被采纳的关键结论转化为具体能力或运行规则。内部建立最小承接链：

> 关键结论 → 具体能力或运行规则 → 用户怎样使用及得到什么结果 → 责任模块 → 初版范围

按以下规则完成转化：

- **能力**说明系统、服务或团队必须支持什么行为，才能直接改善前面识别的问题。
- **运行规则**说明谁发起、谁决定、在什么条件下执行、怎样确认或回退，用于落实难点中的冲突与取舍。
- 最难问题提出的关键冲突必须形成明确取舍，并体现为能力边界或运行规则；不得只保留“兼顾、平衡、提升”等原则表述。
- 多项结论可以由同一项能力共同承接，不为每条结论机械增加功能。
- 无法进入初版的结论要标记为延后，并说明延后原因及其对核心闭环的影响。
- 此处只定义影响方案成立的关键行为与规则，不展开按钮位置、页面布局和低层技术实现。

仅写“对应问题”或重复问题名称不算完成承接。必须说明设计具体做什么，以及它怎样改变用户完成任务的结果。

## 5. 从任务、对象与能力推导架构

同时梳理核心任务流程、核心业务对象和长期共享能力，再划分模块：

- 流程模块负责一个完整任务或稳定阶段。
- 对象模块负责一种需要持续管理的核心业务对象。
- 支撑能力负责跨任务复用的规则、资产、权限或公共服务。
- 共享能力可以放在相关模块内部；只有独立管理价值明确时才成为一级入口。

竞品导航只用于辅助理解其组织方式。当前架构必须依据本项目的任务归属、数据归属和职责关系重新推导。

每个模块说明：

| 字段 | 要求 |
| --- | --- |
| 模块职责 | 负责哪个完整任务、业务对象或稳定能力，产生什么结果 |
| 职责边界 | 与相邻模块如何分工，哪个模块拥有最终责任 |
| 关键能力与运行规则 | 承接哪些关键结论，系统支持什么行为，由谁在什么条件下决定或执行 |
| 必要子菜单 | 支持哪些明确、相互区分的用户任务 |
| 输入与输出 | 接收什么，产生什么，交给下一环节什么 |
| 设计依据 | 对应哪个问题、市场机制和项目取舍 |

为每类数据和关键动作指定唯一责任模块。其他位置可以提供入口或引用，不重复建立数据来源与业务逻辑。子菜单按真实任务设置，不为结构对称增加空模块。

确认架构覆盖从输入到结果、确认、保存或交付的核心任务闭环。

## 6. 按任务尺度选择输出结构

内部研究可以充分，最终正文只保留影响理解和决策的信息。

### 完整设计模式

严格按以下五部分输出，不另建独立的竞品报告、问题优先级或完整研究过程。

### 1. 前期判断

用几句话说明：

- 当前概念要完成什么任务。
- 服务什么人。
- 处于什么阶段。
- 当前最值得确定的方向。

关键词只能作为结尾标签，不能替代解释。

### 2. 最重要的三个问题

每个问题依次说明：

1. 问题具体是什么，以及为什么决定产品价值。
2. 本轮研究中解决得最成熟的第一、第二、第三个案例及其具体方法。
3. 从这些方法中得到的当前结论。

将产品名称链接到支持相应结论的来源。案例与问题放在一起解释，不单独罗列案例卡片。只在影响理解时补充排名依据或证据限制。

### 3. 最难解决的问题

作为独立部分说明：

- 困难来自什么具体冲突、限制或不确定性。
- 冲突会造成什么后果。
- 当前市场采用哪些主要处理方式，以及本轮研究中处理得最成熟的第一、第二、第三个案例分别怎样解决。
- 现有方法仍留下什么缺口。

该问题与第二部分重合时，从“难点与取舍”角度重新解释，不合并章节。

### 4. 综合设计

说明当前项目准备怎样解决：

- 采用哪些成熟机制。
- 借鉴哪些案例的哪些部分。
- 根据当前需求作出哪些调整和取舍。
- 将关键结论落实为哪些具体能力或运行规则，以及它们怎样改善用户结果。
- 初版解决到什么程度，哪些内容延后。

给出清晰的推荐方案。避免重复前三部分已经说明的市场信息。

### 5. 初版架构

必要时先用一条简短流程说明核心任务，再用紧凑表格呈现：

| 模块 | 职责与边界 | 关键能力与运行规则 | 必要子菜单 | 输入与输出 | 承接的问题与机制 |
| --- | --- | --- | --- | --- | --- |

只呈现影响初版方向的一级模块、必要子菜单、职责边界，以及决定方案能否成立的关键能力与运行规则。页面细节、低概率异常和实现方式留到后续阶段。

### 聚焦模式

围绕当前问题直接组织答案，不套用五部分结构。根据实际需要保留：

- 明确结论及必要依据。
- 与当前判断直接有关的案例和机制。
- 当前项目应采用的局部能力、运行规则或取舍。
- 只有在会改变当前决定时，才说明对相邻流程、模块或初版范围的影响。

不输出完整产品范围、三个最重要问题、最难问题、全量延后项或整体架构，除非用户在当前请求中明确要求。

## 7. 控制信息密度

- 让用户能够理解结论，不用关键词代替关键解释。
- 删除不会改变方向、选择、架构或落地判断的信息。
- 每个案例只说明与当前问题有关的机制。
- 不重复同一问题、证据或结论。
- 不展示内部搜索日志、完整候选池或冗长推理过程。
- 不设机械字数上限；根据决策复杂度提供刚好足够的解释。
- 输出长度和研究范围与当前问题尺度一致；聚焦模式在当前判断已经成立时停止。

## 8. 验收并停止研究

输出前先检查是否根据当前请求选择了正确模式，是否把局部问题误扩展成完整设计任务。

聚焦模式检查：

- 聚焦模式是否只回答当前决策，并省略无关的整体问题、完整架构和延后范围。
- 聚焦模式使用的研究、机制和设计影响是否都与当前问题直接相关。

完整设计模式检查：

- 三个重要问题是否直接关联产品价值，彼此是否重复。
- 难点是否说明具体冲突、限制及其后果。
- 标杆结论是否有当前来源，是否解释产品实际采用的方法。
- “机制完整”“适配需求”“效果验证”是否使用了对应强度的证据。
- 综合方案是否考虑机制兼容、当前资源、迁移代价与延后影响。
- 从结论向后检查：每项被采纳的关键结论是否由具体能力或运行规则承接，是否说明用户结果和责任模块；延后项是否说明原因与影响。
- 最难问题中的关键冲突是否形成明确取舍，并落实为能力边界或运行规则。
- 从架构向前检查：每个一级模块和关键能力是否能追溯到问题、市场机制、项目约束或明确取舍。
- 沿核心任务走一遍时，这些能力与规则是否共同解决前面识别的问题；仅有模块名称或“对应问题”标签不算完成承接。
- 架构是否同时覆盖任务流程、核心对象与必要共享能力。
- 模块与子菜单是否职责清晰，数据和关键动作是否有唯一责任归属。
- 初版是否形成完整任务闭环。
- 正文是否只保留当前阶段需要理解的信息，是否存在重复和过度展开。

发现缺口时，只补查或修正对应部分。关键设计选择已有依据、主要架构可以追溯、剩余不确定性已经明确后，结束研究并输出。
